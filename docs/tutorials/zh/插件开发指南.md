# 插件开发指南

这份指南面向会使用 Python、希望为 d3dxSkinManage-Plus 编写扩展工具的开发者。软件按游戏管理 Mod、分类、组合预设和外观变体；插件适合把这些公开能力组合成专门的整理、检查和操作工具。

插件通过 `src.plugin_sdk` 访问宿主，可以拆分为 Python 包、声明插件依赖、按需激活并提交后台任务。第三方 Python 依赖不会自动安装；用户通过压缩包或插件目录安装扩展。

建议先用第 1 节的骨架确认命令可以运行，再按以下顺序阅读三个随包示例。每个示例都有可直接启用的清单、源码、英文语言包和使用说明；无需同时启用。

| 顺序 | 实用示例 | 用途 | 主要教学内容 |
| --- | --- | --- | --- |
| 1 | [Mod 清单导出](../../../plugins/example.mod-inventory/README.md) | 导出当前游戏或分类子树的 CSV 清单 | 多文件组织、按需命令、配置、后台计算与原子文件保存 |
| 2 | [预设检查](../../../plugins/example.preset-audit/README.md) | 找出组合中失效的 Mod 和变体引用 | 未解析引用、启动激活、页面、事件、分批查询与清理 |
| 3 | [预设轮换](../../../plugins/example.preset-cycle/README.md) | 通过快捷键或按钮切换前后组合 | 写权限、异步任务、重复请求、完成反馈与取消 |

第 10 节给出逐个示例的阅读和练习步骤。接口查询见第 2–9 节，自定义界面见第 11 节，开发验证和排障见第 12 节。

## 1. 环境与第一个插件

### 1.1 准备环境

使用 Windows 10/11 x64 和 Python 3.10–3.14，推荐在源码环境中开发。在仓库根目录运行；已有开发环境时跳过前两条：

```powershell
python -m venv .venv
& ".venv/Scripts/python.exe" -m pip install -e ".[dev]"
& ".venv/Scripts/python.exe" run_app.py
```

先确认主程序可以启动，再添加一个测试游戏和少量占位 Mod。第一个插件只读取数据；预设轮换会改变部署，应在测试库检查成功、失败和取消结果。

### 1.2 生成并启用骨架

```powershell
& ".venv/Scripts/python.exe" scripts/plugins/new_plugin.py com.example.mod-summary --name "Mod 统计助手" --author "示例作者"
```

生成的目录为：

```text
plugins/com.example.mod-summary/
├── plugin.json
├── entry.py
├── commands.py
├── languages/en-US/strings.json
└── README.md
```

在应用「插件」页点击「打开插件目录」，确认可以看到这个文件夹，然后「重新扫描」并开启插件，阅读首次信任与权限提示。在工具箱或导航区「插件命令」中执行「查看 Mod 统计」，会显示当前游戏的 Mod 总数和已启用数；未选游戏时会提示先选择游戏。

默认快捷键是 `Ctrl+Alt+M`，可在「设置 → 快捷键」中调整。冲突时不会覆盖已有绑定。命令返回的 Python 字典供调用者使用，可见提示由插件自己调用 `notify()` 显示。

目标目录已存在时，脚手架停止且不覆盖文件。`--dir` 指定插件目录的父目录，例如 `--dir "$env:TEMP/plugin-demo"` 输出 `$env:TEMP/plugin-demo/com.example.mod-summary/`；宿主只扫描实际插件目录，不会自动扫描其他开发目录。

### 1.3 理解最小实现

脚手架将生命周期与命令逻辑分别放在 `entry.py` 和 `commands.py`。下面是便于手动创建的单入口最小插件。文件用 UTF-8 保存，清单必须是标准 JSON。

`plugin.json`：

```json
{
  "id": "com.example.mod-summary",
  "name": "Mod 统计助手",
  "version": "0.1.0",
  "apiVersion": "2.0",
  "minAppVersion": "0.1.0",
  "author": "示例作者",
  "description": "Mod 统计助手 插件",
  "entry": "entry.py",
  "files": ["entry.py"],
  "permissions": ["mods:read", "ui:tools-page", "ui:shortcuts"],
  "contributes": {
    "commands": [
      {"id": "com.example.mod-summary.summary", "title": "查看 Mod 统计"}
    ],
    "toolsPage": [
      {"command": "com.example.mod-summary.summary", "group": "插件"}
    ],
    "shortcuts": [
      {"command": "com.example.mod-summary.summary", "default": "Ctrl+Alt+M", "context": "window"}
    ]
  }
}
```

`entry.py`：

```python
"""插件入口：只依赖公开 SDK。"""

from __future__ import annotations

from src.plugin_sdk import PluginBase, PluginContext


class Plugin(PluginBase):
    """通过公开 SDK 查询当前游戏并显示 Mod 启用数量。"""

    def activate(self, ctx: PluginContext) -> None:
        """保存插件上下文并注册统计命令。"""
        self._ctx = ctx
        ctx.commands.register("com.example.mod-summary.summary", self._summary)
        ctx.logger.info("插件已激活：%s", ctx.meta.name)

    def _summary(self, **_) -> dict[str, int]:
        """显示当前游戏的 Mod 总数与启用数，并返回可供其他命令使用的结果。"""
        tr = self._ctx.i18n.t
        if not self._ctx.game.current_game_id():
            self._ctx.ui.notify(tr("请先选择一个游戏。"), "warning")
            return {"mods": 0, "enabled": 0}
        mods = self._ctx.mods.get_mods()
        enabled = sum(mod.enabled for mod in mods)
        self._ctx.ui.notify(tr("共 {total} 个 Mod，已启用 {enabled} 个。", total=len(mods), enabled=enabled))
        return {"mods": len(mods), "enabled": enabled}

    def deactivate(self) -> None:
        """记录插件停用日志。"""
        self._ctx.logger.info("插件已停用：%s", self._ctx.meta.name)
```

清单声明用户看到的入口，`activate()` 将命令 ID 绑定到处理函数。清单与注册 ID 必须相同。每次执行时重新查询当前游戏，不把旧快照当成实时模型。

声明的命令会自动成为激活入口，因此不必再写 `onCommand`。启用后显示「待命」是正常状态：宿主已经登记按钮和快捷键，首次使用时才执行入口。语言包格式见第 7.5 节。

### 1.4 按项目风格继续开发

编写插件时可遵循以下代码规范，三个随包示例也采用这些约定：

- Python 使用四空格缩进、双引号、120 字符行宽、LF 换行；Ruff 版本由 `pyproject.toml` 固定。
- 使用 `snake_case` 标识符、现代类型标注，以及简明的中文模块、类和函数文档字符串。Qt 重写方法保留接口规定的名称。
- 用户可见文案通过 `ctx.i18n.t()` 翻译；命令 ID、设置键和持久身份保持稳定，日志用中文说明操作。
- 将快照转换、引用判断、候选选择等纯逻辑与 Qt 控件和任务回调分开，避免在插件中复制宿主内部实现。
- 需要宿主能力时只导入公开 SDK；使用标准 PySide6 控件和宿主主题，避免写死颜色。

要基于某个实用示例开发，复制对应目录，修改 `plugin.json` 的 `id`、名称及所有贡献点 ID。三个示例在代码中用 `ctx.plugin_id` 拼接命令或页面 ID，清单中的前缀仍需同步更换。修改后重载，按第 12 节验证。

## 2. 目录与加载契约

- 唯一加载位置是应用根目录的 `plugins/`：从源码运行时为仓库根目录，运行发行包时为 exe 所在目录；Nuitka 单文件使用外层启动器所在目录。
- 「打开插件目录」、压缩包安装、重新扫描和重载使用同一目录；列表不会从源码包或已保存的启用记录补出不存在的插件。
- 所有插件（含随包示例）使用相同的信任、权限和卸载规则。首次启用需确认信任；移除目录后重新扫描会停用并移除对应记录。
- 程序目录不可写时，遵循应用统一的数据目录回退；以「打开插件目录」显示的实际位置为准。
- 一个插件 = 一个目录，**必须**含 `plugin.json`。
- `plugin.json` 的 `entry` 指向一个 `.py`，其中**必须导出名为 `Plugin` 的类**，继承 `src.plugin_sdk.PluginBase`。
- 访问宿主代码时，**只导入** `src.plugin_sdk` 及其子模块；导入 `src.core`、`src.ui` 等内部模块会被安全扫描拦截。Python 标准库、宿主已有的第三方库和 PySide6 控件仍可按权限使用。
- 宿主为每次加载创建独立包命名空间，支持 `from .commands import show_summary`、嵌套子包及包内资源。不要用 `import helper` 导入同目录文件，或修改全局 `sys.path`。
- 重载读取当前源码，清除插件全部子模块与导入查找器；文件大小和时间戳相同的修改也不会命中旧字节码。共享第三方依赖不会被插件重载移除。

## 3. plugin.json 字段

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | ✓ | 全局唯一，反向域名风格，仅限字母数字 `. _ -`，2~64 位 |
| `name` `version` | ✓ | 显示名 / 语义化版本 |
| `apiVersion` | ✓ | 所需 SDK 版本，当前 `"2.0"`；主版本必须相同，所需次版本不得高于宿主 |
| `entry` | ✓ | 插件目录内的相对 `.py` 路径，导出 `Plugin` 类；禁止绝对路径、`..` 和越界链接 |
| `minAppVersion` | | 最低应用版本，如 `"0.1.0"`；加载代码前检查，不满足则拒载 |
| `author` `description` `homepage` | | 元信息 |
| `permissions` | | 见 §6 |
| `contributes` | | 见 §5 |
| `activationEvents` | | 显式激活条件，默认空数组；命令与视图条件自动推导，见 §4 |
| `dependencies` | | 插件 ID 到版本区间的映射，见 §4.2；不会自动安装或授权依赖 |
| `files` | | 打包所包含的相对文件或目录，打包工具要求显式声明；不使用通配符 |
| `$schema` | | 编辑器校验地址；仓库插件可填 `../../docs/plugin.schema.json` |

[JSON Schema](../../plugin.schema.json) 提供编辑器补全。宿主还会检查命令命名空间、重复声明、菜单/快捷键引用、设置默认值、入口路径及依赖区间。未知字段、未知权限和无效声明会直接报错，不会静默忽略。

## 4. 生命周期

### 4.1 发现与激活

发现阶段只解析清单，不执行插件代码。已启用且受信任、版本和依赖均满足的插件进入 `ready`；命令、菜单、快捷键和设置可以立即显示。

| 激活条件 | 触发方式 |
| --- | --- |
| `onCommand:<命令 ID>` | 第一次执行本插件命令；从 `contributes.commands` 自动推导 |
| `onView:<视图 ID>` | 首次打开相应插件详情视图；从 `contributes.views` 自动推导 |
| `onEvent:<事件名>` | 收到 §7.3 的宿主事件；先激活，再交付这一次事件 |
| `onStartup` | 启动或重新扫描后立即激活；用于需要常驻事件或动态导航页的插件 |

例如 `"activationEvents": ["onEvent:game_changed"]` 在首次游戏切换时启动。声明的命令和视图无需重复写进数组；只被其他插件使用的服务可以不声明激活事件，由消费者按依赖关系启动。

```python
from src.plugin_sdk import PluginBase, PluginContext


class Plugin(PluginBase):
    """描述本插件提供的业务功能。"""

    def activate(self, ctx: PluginContext) -> None:
        """保存上下文并注册命令、事件或界面工厂。"""
        ...

    def deactivate(self) -> None:
        """停止插件自有任务；注册资源由宿主统一清理。"""
        ...
```

- 抛异常会被**熔断**：记录错误、自动停用该插件，宿主不受影响。
- 命令/事件处理函数抛异常同样熔断。
- 运行状态包括 `discovered`（等待信任）、`ready`、`activating`、`active`、`blocked`（依赖不可用）、`disabled` 和 `error`。管理详情的「权限与来源」可查看依赖、激活原因及加载/激活耗时。
- 重新扫描先完整停用旧实例，再发现并登记贡献。重载或更新某个依赖时，先停用其传递消费者，再重建之前活动的消费者；无关插件保持运行。
- 停用、重载、卸载会取消尚未完成的操作并移除任务回调。已经完成的文件操作由宿主安全提交。`deactivate()` 仍应释放插件自己的定时器、线程和其他资源。
- 停用后旧 `ctx` 的业务写操作返回失败任务，查询、存储、配置、命令、事件、UI 和后台任务入口拒绝继续使用。`deactivate()` 用于释放自有资源，此时不能再查询或修改宿主；元信息与日志仍可用于诊断。

### 4.2 插件依赖与公开 API

消费者在清单中声明 `"dependencies": {"com.example.provider": "^1.2.0"}`。宿主先验证整个依赖图，再按依赖在前的顺序激活。缺失、未启用、未受信任、版本不符或循环依赖会阻止消费者导入，并显示具体原因。依赖故障会停止消费者，但保留消费者的启用意愿；恢复依赖后可以再次使用。

| 约束 | 接受的版本 |
| --- | --- |
| `1.2.3` | 相同语义版本，忽略 `+build` 标识 |
| `*` | 任意正式版本 |
| `^1.2.3` | `>=1.2.3 <2.0.0` |
| `^0.2.3` / `^0.0.3` | 分别到下一次版本 / 下一修订版本之前 |
| `~1.2.3` | `>=1.2.3 <1.3.0` |
| `>=1.2.0 <2.0.0` | 以空格分隔的比较条件同时满足 |

支持 `= > >= < <=`，不支持 `||`、通配版本片段或连字符范围。预发布版本只有在区间明确包含同一三段版本的预发布边界时才被接受，例如 `>=1.1.0-beta.1 <1.1.0`。

服务插件可以从 `activate()` 返回自己的 API 对象；消费者在 `activate()` 中用 `ctx.extensions.get_exports("com.example.provider")` 获取它。未声明的依赖会抛 `PluginError`。导出对象只在当前激活周期内有效，依赖重载时消费者也会重建；不要将 API 对象写入持久存储。接口签名由两个插件约定，版本区间表达这个约定。跨插件命令也可以通过 `ctx.commands.execute()` 组合。

### 4.3 资源作用域

`ctx.events.on()`、`ctx.commands.register()`、`ctx.ui.register_view()` 和 `ctx.ui.register_page()` 返回 `Disposable`，宿主同时自动登记所有权。调用句柄的 `dispose()` 可提前注销；重复释放不会产生副作用。替换命令后，旧句柄不会移除新处理器。

自建资源通过 `ctx.subscriptions.add(cleanup_callback)` 或 `add(实现 dispose() 的对象)` 托管。集合按逆序释放，单项清理失败会记录日志并继续清理其他资源。`DisposableStore` 支持嵌套和 `with`，适合一个页面或某次操作的局部订阅。后台任务和配置订阅同样返回句柄，可放入该集合。

```python
from src.plugin_sdk import DisposableStore
from src.plugin_sdk.events import GAME_CHANGED


def observe_game(ctx, callback):
    """建立可独立关闭的观察作用域，同时交给插件上下文兜底清理。"""
    scope = ctx.subscriptions.add(DisposableStore())
    scope.add(ctx.events.on(GAME_CHANGED, callback))
    return scope
```

## 5. 贡献点（contributes）

```jsonc
"contributes": {
  "commands":  [{ "id": "myplugin.scan", "title": "扫描" }, { "id": "myplugin.inspect", "title": "检查" }],
  "shortcuts": [{ "command": "myplugin.scan", "default": "Ctrl+Alt+S", "context": "window" }],
  "toolsPage": [{ "command": "myplugin.scan", "group": "插件", "icon": "navigation/tools" }],
  "menus":     { "mod-context": [{ "command": "myplugin.inspect", "when": "modSelected" }] },
  "settings":  [{ "key": "threshold", "type": "int", "default": 2, "title": "阈值" }],
  "views":     [{ "id": "myplugin.panel", "title": "我的面板" }]
}
```

| 贡献点 | 渲染位置 | 说明 |
|--------|----------|------|
| `commands` | — | 一切贡献点的执行单元；用 `ctx.commands.register(id, handler)` 实现 |
| `toolsPage` | 工具页「插件」分组按钮 | 点击执行 `command` |
| `menus."mod-context"` | Mod 卡右键菜单 | 命令收 `mod_id` 关键字；`when` 支持 `modSelected`/`always` |
| `menus."character-context"` | 角色卡右键菜单 | 命令收 `node_id` 关键字；`when` 支持 `characterSelected`/`always` |
| （全局命令）| 导航区「插件命令」按钮 | 所有插件 `commands` 自动汇入该按钮的命令面板（无需声明），点击直接执行 |
| `settings` | 插件详情 | 类型 `bool`/`int`/`float`/`str`，支持范围、长度与枚举，使用 `ctx.configuration` |
| `views` | 插件页该插件卡内 | 用 `ctx.ui.register_view(view_id, factory)` 提供 QWidget 工厂 |
| `shortcuts` | 设置 → 快捷键中的插件分组 | 声明命令默认按键及焦点上下文；需要 `ui:shortcuts` |

命令 ID 必须以完整插件 ID 加 `.` 为前缀（如 `com.example.mod-summary.summary`）。同一插件可更新自己的处理函数，不能覆盖其他插件的命令。菜单、工具按钮和快捷键必须引用本插件声明的命令，所有声明命令必须在 `activate()` 返回前注册；缺失处理器会使激活失败并撤销全部贡献。

`context` 默认 `window`，也可为 `overview`（类别总览列表）或 `preset`（预设列表）。按键复用宿主冲突检查、文本编辑优先级、输入法组合输入和弹窗规则；系统保留键不能绑定。插件快捷键只在应用内生效。默认键遇到已有绑定时不覆盖它，新命令的“未绑定”状态会持久保存，重启／重载不改变已分配的按键；用户可在设置中改绑或恢复默认。改绑即时生效，停用／重载／错误熔断／卸载会撤销活跃绑定，保留用户偏好供下次启用。

## 6. 权限（permissions）

声明在 `plugin.json`，首次启用时确认信任与申请权限。宿主持久化已确认的权限；更新或重扫发现新增权限时须重新确认。未知权限使清单校验失败。SDK 方法缺少对应权限时抛 `PermissionDenied`。

| 权限 | 解锁能力 |
|------|----------|
| `mods:read` | 查询游戏、Mod、分类、预设与变体；查询前强制检查 |
| `mods:write` | Mod 启用／禁用，以及预设和变体的创建、应用、复制、修改 |
| `mods:manage` | `ctx.mods.delete_mod`、`ctx.presets.delete`、`ctx.variants.delete` |
| `storage` | 访问私有 KV、数据目录和声明配置；运行时检查 |
| `ui:tools-page` / `ui:menus` / `ui:settings` | 声明相应贡献；清单检查，设置还需 `storage` |
| `ui:views` | 视图、动态页面和对话框；清单与 SDK 方法均检查 |
| `ui:shortcuts` | 向宿主设置与分派器注册本插件快捷键；清单解析和激活时检查 |
| `network` | 导入 `socket/httpx/requests/urllib/...` |
| `process` | 导入 `subprocess/multiprocessing` |
| `native` | 导入 `ctypes/cffi/winreg` |
| `fs:read` / `fs:write` | 文件读写（约定）|
| `background` | 使用 `ctx.tasks.run()`；不会使其他 SDK 方法变成线程安全接口 |

**安全扫描**（加载前 AST）：禁止 import 宿主内部；上述危险模块须声明对应权限；禁用 `eval/exec/compile/__import__/os.system/os.popen`。

外部插件仍是在应用进程中执行的 Python 代码。静态扫描和 SDK 权限门控是检查与授权机制，不是防御恶意代码的完整沙箱；只安装可信来源插件。后台执行与清理约定见第 9 节。

### 7.1 只读视图与身份

`ModInfo` 是不可变快照，包含 `mod_id`、`name`、`author`、`enabled`、`node_id`、`game_id`、`rating`、`tags`。作者、分级和标签来自保存的 Mod 元数据；`rating` 为 `G/P/R/X`，`tags` 为元组。快照不会随宿主变化自动更新，收到事件后重新查询。

`mod_id` 是持久身份，可直接保存在插件存储中，下次用 `get_mod(mod_id)` 查询；索引重建不改变此身份，删除后查询返回 `None`。`get_mod()` 可跨游戏读取，`game_id` 始终是该 Mod 的真实归属。`get_mods()`、`search()` 和角色查询面向当前游戏；读到其他游戏的对象并不允许跨游戏写入。

`CharacterInfo` 包含 `id`、`name`、`name_en`、`parent_id`、`game_id`、`node_type`。`parent_id` 表示父节点，`node_type` 为 `category` 或 `character`；`get_mods(node_id)` 取该节点直接关联的 Mod，不展开整棵子树。

### 7.2 操作任务

写操作的返回值表示任务，不表示成功。用 `task.done` / `task.result` 读取状态，或用 `task.on_finished(callback)` 接收 `OperationResult`。已完成任务注册回调时会立即调用，所以不要依赖回调一定延迟到下一轮事件循环。

```python
from src.plugin_sdk import OperationResult, OperationTask


def enable_mod(self, mod_id: str) -> OperationTask:
    """提交启用请求，通过完成回调观察实际结果。"""
    task = self._ctx.mods.set_enabled(mod_id, True)
    task.on_finished(self._enabled)
    return task


def _enabled(self, result: OperationResult) -> None:
    """区分成功与未全部完成的任务结果。"""
    if result.ok:
        self._ctx.logger.info("实际完成 %d 项", len(result.succeeded_ids))
    else:
        self._ctx.logger.warning("操作未全部完成：%s", result.error)
```

`OperationResult` 包含：

| 字段 | 含义 |
|------|------|
| `game_id` | 请求发起时的游戏 |
| `succeeded_ids` | 已成功达到目标状态的持久 Mod ID 元组 |
| `failed_ids` | 失败的 ID 元组 |
| `cancelled_ids` | 取消、尚未完成的 ID 元组 |
| `error` | 失败／取消原因或提交后的收尾诊断；正常完成时为空字符串 |
| `preset_id` | 请求对应的组合预设 ID；创建／复制成功后为新 ID，无预设时为空字符串 |
| `variant_id` | 请求对应的命名变体 ID；保存／复制成功后为新 ID，工作状态或无变体时为 `None` |
| `ok` | 无失败、取消和错误时为 `True`；空批次也可成功 |

请求固定到发起时的游戏。游戏发生变化、目标不属于当前游戏、没有部署目录、存在冲突的宿主任务等情况会通过结果报告失败；不要将调用次数统计成成功数。批量操作可部分成功，应同时检查三组 ID 和 `error`。

已提交的变体操作即使随后读取列表失败，仍保留在 `succeeded_ids` 中，并返回对应的 `variant_id`；读取错误写入 `error`，此时 `ok` 为 `False`。不要仅因诊断非空就把成功项当成未执行并重复提交。

`set_enabled(id, True/False)` 指定目标状态，已处于该状态时直接报告成功。`toggle_mod(id)` 在任务执行时读取当前状态并切换。`disable_all()` 禁用当前游戏已启用的 Mod，传 `node_id` 则只处理该节点的 Mod。禁用沿用宿主的变体收集、INI 同步、部署暂存、部署记录和预设处理；仅成功项移出当前预设。`delete_mod()` 遵循应用设置中的永久删除/回收站策略。

调用 `task.cancel()` 请求在安全边界停止。Mod 操作和已完成的变体事务可能继续提交并计入成功项；组合预设应用在提交前取消会尝试事务回滚，提交后继续完成收尾。始终检查最终 `OperationResult`。只有预设元信息变化的操作可以没有受影响的 Mod ID，仍需检查 `ok` 和 `error`。插件停用后，宿主移除其尚未触发的完成回调。

SDK 读写、事件、命令、完成回调和 Qt 控件访问都应在宿主主线程运行。归档部署和批量禁用的文件 IO 由宿主在后台完成；不要在 GUI 回调中循环等待 `done`、调用 `sleep` 或自行访问 SQLite。多步操作应通过完成回调串接，例如先确认 `disable_all()` 成功，再启用替代 Mod。第 10.3 节的预设轮换示例展示了忙碌状态、立即完成回调和停用取消的处理。删除操作不保证全部文件 IO 都在后台执行。

### 7.3 事件

从 `src.plugin_sdk.events` 导入常量，使用 `ctx.events.on(EVENT, handler)` 订阅。处理函数以关键字接收 payload，例如 `def on(self, mod_id="", game_id="", **_): ...`。

| 常量 | 事件名 | payload |
|------|--------|---------|
| `MOD_IMPORTED` | `mod_imported` | `mod_id`, `node_id`, `game_id` |
| `MOD_ENABLED` | `mod_enabled` | `mod_id`, `game_id` |
| `MOD_DISABLED` | `mod_disabled` | `mod_id`, `game_id` |
| `MOD_DELETED` | `mod_deleted` | `mod_id`, `game_id` |
| `GAME_CHANGED` | `game_changed` | `game_id` |
| `PRESET_APPLIED` | `preset_applied` | `affected_ids`, `game_id` |
| `MOD_METADATA_CHANGED` | `mod_metadata_changed` | `mod_id`, `game_id` |
| `TAGS_CHANGED` | `tags_changed` | `affected_ids`, `game_id` |
| `MOD_UPDATED` | `mod_updated` | `mod_id`, `game_id` |
| `INDEX_REBUILT` | `index_rebuilt` | `game_id` |
| `VARIANT_RESTORED` | `variant_restored` | `mod_id`, `game_id`, `applied`, `removed_keys` |
| `VARIANT_STATE_CHANGED` | `variant_state_changed` | `mod_id`, `game_id` |
| `VARIANT_REFERENCES_MISSING` | `variant_references_missing` | `game_id`, `preset_id`, `mod_ids`, `names` |

Mod 数据变更事件在相应业务提交后发出。标签修改同时影响 Mod 元数据时会有两种事件；不要把不同类型的通知当作重复操作。`VARIANT_RESTORED` 表示变体恢复已经执行，可能发生在预设整体提交之前；预设级恢复的 `mod_id` 可以为空，整体完成应观察 `PRESET_APPLIED`。`VARIANT_STATE_CHANGED` 提示重新查询该 Mod 的变体快照；`VARIANT_REFERENCES_MISSING` 表示组合提交时存在缺失的变体引用，`mod_ids` 为持久 Mod ID，`names` 用于显示。索引重建只使快照失效，持久引用仍用 `mod_id` 查询。

### 7.4 组合预设与命名变体

```python
ctx.presets.get_presets() -> list[PresetInfo]  # 当前游戏
ctx.presets.get_preset(preset_id) -> PresetInfo | None
ctx.presets.get_current() -> PresetInfo | None
ctx.presets.create(name, description="") -> OperationTask
ctx.presets.duplicate(preset_id, name=None) -> OperationTask
ctx.presets.rename(preset_id, name) -> OperationTask
ctx.presets.update_description(preset_id, description) -> OperationTask
ctx.presets.apply(preset_id) -> OperationTask
ctx.presets.delete(preset_id) -> OperationTask  # mods:manage；拒绝默认／当前预设

ctx.variants.get_variants(mod_id) -> list[VariantInfo]
ctx.variants.get_state(mod_id) -> VariantStateInfo
ctx.variants.save(mod_id, name, use_defaults=False) -> OperationTask
ctx.variants.update(mod_id, variant_id, use_defaults=False) -> OperationTask
ctx.variants.apply(mod_id, variant_id=None) -> OperationTask
ctx.variants.rename(mod_id, variant_id, name) -> OperationTask
ctx.variants.duplicate(mod_id, variant_id, name=None) -> OperationTask
ctx.variants.delete(mod_id, variant_id) -> OperationTask  # mods:manage
```

`create()` 的 `description`、复制时的 `name`、`use_defaults` 均为仅限关键字参数。`create()` 创建空组合，`duplicate()` 复制已有组合及其变体引用。变体 `save()` 保存当前状态；`update()` 更新内容并保留身份和名称；`use_defaults=True` 明确使用默认值。`apply(mod_id, None)` 取消命名变体选择并恢复默认配置，传入命名变体 ID 则应用该变体。变体能力仍受当前 Mod 是否支持持久化变量、是否存在活动事务等宿主条件约束。

`PresetInfo` 含 `preset_id, game_id, name, description, is_default, enabled_mod_ids, node_mods, mod_variants, unresolved_mod_ids`。两个映射只读，内部列表复制为元组。`unresolved_mod_ids` 返回已保存但当前索引无法解析的 Mod 身份；`enabled_mod_ids` 和 `node_mods` 表示已解析成员。索引恢复后应重新查询，不要把未解析直接当成永久删除。`VariantInfo` 含 `variant_id, mod_id, game_id, name, variables, created_at, updated_at, source_content_hash, declaration_fingerprint`；`variables` 为 `VariantVariableInfo` 元组，字段为 `ini_path, variable, namespace_mode, value, namespace`。INI 路径是变体变量的相对标识，不是宿主文件访问入口。

`VariantStateInfo` 含 `mod_id, game_id, enabled, selected_variant_id, status, can_save, reason, captured_at, variable_count, confirmed_count, source_changed`。收到状态事件后重新查询，不要修改内部容器、INI 或数据库。快照类型分别从 `src.plugin_sdk.presets` 和 `src.plugin_sdk.variants` 导入。

```python
from src.plugin_sdk import OperationResult


def saved(result: OperationResult) -> None:
    """在创建完成后按返回的稳定 ID 查询预设。"""
    if result.ok:
        preset = ctx.presets.get_preset(result.preset_id)
        if preset is not None:
            ctx.logger.info("新预设：%s", preset.name)
    else:
        ctx.logger.warning("预设未创建：%s", result.error)


ctx.presets.create("插件创建的组合", description="空组合").on_finished(saved)
```

### 7.5 插件语言包

`ctx.i18n.t(source, **values)` 从插件目录的 `languages/<locale>/strings.json` 读取翻译，`ctx.i18n.language` 跟随宿主当前语言。每个插件独立解析语言包，不会覆盖宿主或其他插件的文案，也不提供修改宿主语言的入口。

```json
{
  "_meta": {"format": 1, "name": "English", "fallback": "zh-CN"},
  "messages": {"共 {count} 项": "{count} items", "扫描": "Scan"}
}
```

占位符名必须与原文相同。缺失／非法翻译回退到声明的备用语言及原文并记录诊断。显示名、说明和贡献点标题使用同一语言包，命令 ID、设置键和值保持原始身份。控件使用 `ctx.i18n.t()` 设置文本；下拉框把翻译作为显示文本，把稳定值放在 `userData`。已构造界面沿用宿主语言设置的重启规则；修改语言包后重载插件重新读取。
