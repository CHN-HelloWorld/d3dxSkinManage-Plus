# Windows 构建与发布指南

本指南涵盖 Windows 主程序、原生更新器和发行 ZIP 的本地构建，以及 GitHub 云端构建与发布。
运行及构建依赖统一声明于 [pyproject.toml](../pyproject.toml)。

- [本地构建](#本地构建)：准备本机环境，选择构建模式并生成发行包。
- [云端构建与发布](#云端构建与发布)：配置视频资源，通过 GitHub Actions 构建或发布版本。
- [包体与依赖报告](#包体与依赖报告)：了解运行库、包体大小和编译诊断报告。
- [发行内容](#发行内容)：了解两种构建方式共用的打包规则、许可材料和发行前验证。

## 本地构建

### 环境

主程序需要 Windows x64、Python 3.10–3.14 和项目运行依赖。Nuitka 编译依赖通过同一个
Python 解释器安装，避免构建时缺少运行库。

原生更新器使用 Visual Studio 2022、MSVC v143 和 Windows SDK，具体步骤见
[更新器说明](../updater/README.md)。
完整发行包还需按[短片资源说明](../resources/about/story/README.md)准备独立视频资源。

```powershell
.venv\Scripts\python.exe scripts/release/build.py --install-deps --check
```

项目路径含非 ASCII 字符时，构建脚本使用按仓库路径区分的 ASCII 暂存目录，完成后将产物放回
项目 `build/`。暂存目录与当前仓库绑定，清理时不会删除其他仓库的构建结果。

### 构建选项

```powershell
# 可分发的程序文件夹
.venv\Scripts\python.exe scripts/release/build.py

# 单文件主程序；外置配置和媒体仍需随包分发
.venv\Scripts\python.exe scripts/release/build.py --onefile

# 保留诊断控制台
.venv\Scripts\python.exe scripts/release/build.py --console

# 包含已经编译的原生更新器，并生成发行 ZIP
.venv\Scripts\python.exe scripts/release/build.py --with-updater --zip

# 查看编译命令
.venv\Scripts\python.exe scripts/release/build.py --dry-run

# 清理本仓库的构建产物和暂存目录
.venv\Scripts\python.exe scripts/release/build.py --clean
```

`--` 后的选项传递给 Nuitka。根目录的 `构建工具.bat` 提供相同操作的交互入口。

## 云端构建与发布

[Windows 构建与发布](../.github/workflows/release.yml) 在 GitHub 的 Windows x64 环境中构建主程序、
原生更新器和完整发行 ZIP。只有手动运行时才会启动；普通推送和 PR 不触发构建或质量检查。
构建环境固定为 Windows Server 2022、Python 3.14 x64 和 MSVC，与本地完整构建使用同一打包入口。

`build` 模式生成可下载的构建产物，`publish` 模式在构建成功后创建 GitHub Release。
发布标题和正文由维护者填写，程序的更新窗口直接读取这些内容。

### 首次配置

1. 将工作流、发布脚本及其他源码推送到 GitHub 仓库，确保默认分支中有 `release.yml`。
   仓库需要允许使用 GitHub Actions；工作流使用自动提供的 `GITHUB_TOKEN`，不需要另建个人令牌。
2. 在本地仓库根目录制作独立视频资源包：

   ```powershell
   .venv\Scripts\python.exe scripts/release/github_release.py pack-media
   ```

   输出为 `build/d3dxSkinManage-Plus-story-media.zip`。脚本会先核对
   [媒体清单](../resources/about/story/media-manifest.json)中的文件大小和 SHA256。
   本地视频应位于 `resources/about/story/film.mp4`；获取方式见[短片资源说明](../resources/about/story/README.md)。
3. 在 GitHub 的 **Releases → Draft a new release** 创建资源发布：
   - Tag：`build-resources`。
   - 标题：例如“构建资源”；正文可说明这是云端构建所需的视频包。
   - 附件：上传 `d3dxSkinManage-Plus-story-media.zip`。
   - 勾选 **Set as a pre-release**，然后发布，不要保留为草稿。

资源 Release 只需配置一次。使用预发布可以让主程序的正式版本检查和版本历史忽略它。
如已有其他资源 tag，可在 **Settings → Secrets and variables → Actions → Variables** 添加
仓库变量 `STORY_MEDIA_TAG`，值设为该 tag；未设置时使用 `build-resources`。

视频不进入 Git。每次云端构建都会下载资源包，只恢复清单指定的视频，并验证大小和摘要。
更换视频时需要同步修改媒体清单，再重新制作、上传资源包。

供主程序在线更新的仓库需要可公开访问；当前更新器不使用 GitHub 登录令牌。
私有仓库仍可使用云端构建，并由有权限的成员下载 Actions 产物。

### 构建并发布一个版本

1. 打开仓库 **Actions → Windows 构建与发布 → Run workflow**。
2. 在 **Use workflow from** 选择本次要构建的分支，填写下列输入：

   | 字段 | 填写方式 |
   | --- | --- |
   | `mode` | 选择 `publish`。 |
   | `version` | 例如 `0.1.1` 或 `v0.1.1`。支持三段或四段数字，每段为 0–65535，不带前导零或 `beta` 等后缀。 |
   | `release_title` | 必填，例如 `v0.1.1 · 更新体验改进`。对应 GitHub Release 标题和程序更新窗口的版本说明标题。 |
   | `release_notes` | 必填，填写本次更新的 Markdown 正文；网页单行输入框可使用字面的 `\n` 表示换行。 |

3. 点击 **Run workflow**，等待“构建 Windows x64”和“发布 GitHub Release”成功。
4. 在 **Releases** 页面获取正式版本；工作流运行摘要也会提供发布链接。

网页正文输入示例：

```text
## 更新内容\n\n- 改进 Mod 管理体验\n- 修复更新窗口显示问题\n\n## 使用说明\n\n解压后运行主程序。
```

工作流会将它还原为多行 Markdown。复杂正文也可以保存为 UTF-8 文件，再通过 GitHub CLI 提交：

```powershell
gh workflow run release.yml --ref main `
  -f mode=publish `
  -f version=0.1.1 `
  -f 'release_title=v0.1.1 · 更新体验改进' `
  -F 'release_notes=@release-notes.md'
```

实际多行正文会原样保留，包括 Windows 路径中的反斜杠。不要在正文中复制旧版本的
`SHA256: ...` 校验值；工作流会为本次 ZIP 自动生成校验文件，并将校验值作为隐藏的 HTML 注释附在正文末尾。

### 只构建，不发布

同样手动运行工作流，将 `mode` 设为 `build`，填写 `version` 即可，标题和正文可以留空。
成功后在该次运行页面的 **Artifacts** 下载 `windows-v版本号`，有效期为 14 天。

解开 Actions 的产物归档后，里面包含：

- `d3dxSkinManage-Plus-v版本号-win64.zip`：实际程序发行包。
- 同名 `.zip.sha256` 文件：发行包校验值。
- `release-notes.md` 和 `release.json`：本次构建的发布说明和元数据。

正式发布只附加程序 ZIP 和校验文件。编译诊断报告单独保存为 `nuitka-report-运行编号`，有效期为 7 天。
程序发行包的具体内容见下方[发行内容](#发行内容)。

### 与主程序更新功能的关系

工作流只在云端构建目录内更新以下内容，不会额外向源码分支提交版本修改：

- 主程序 `APP_VERSION`、Python 包版本和更新器文件版本使用填写的 `version`。
- 主程序默认更新源使用当前 GitHub 仓库的 `owner/repo`。
- Release tag 自动使用 `v版本号`，指向启动本次工作流时所选分支的提交。
- Release 的 `name` 使用指定标题，`body` 使用指定正文；程序从正式版本的 `/releases/latest` 读取它们。

无需提前创建版本 tag。已有 tag 必须指向本次构建的提交，已经公开发布的同版本 Release 不会被覆盖。
新版本号应高于用户已安装的版本，程序才会提示更新。现有安装若手动配置了其他更新仓库，
该设置仍然优先于构建时写入的默认更新源。

发布任务会先创建草稿，上传 ZIP 和校验文件，确认附件大小、上传状态及 GitHub 提供的摘要后，
才公开为正式版本并标记为 Latest。上传失败时草稿保持未发布状态，主程序不会将它识别为新版本。
可以在运行页面选择 **Re-run failed jobs**，复用已完成的构建产物继续发布；同一版本、同一源码提交的草稿会被复用。
若产物已经超过保留期限，需要重新运行全部任务。草稿属于其他提交时，应使用新的版本号或先处理旧草稿。

## 包体与依赖报告

默认使用目录模式，配合 `--zip` 生成下载包。目录内仍需携带 Python、Qt、NumPy 等运行库，
单文件模式只是改变分发与解压方式，并不消除这些依赖。

编译时会加载 `scripts/release/nuitka-package.config.yml`：将 `windows-capture==2.0.1` 的图片保存入口
改为使用已有的 Pillow，并排除 OpenCV。原生捕获、NumPy 帧处理及 Qt 多媒体插件保持可用。
此替换只作用于编译产物；开发环境仍按上游依赖声明安装 OpenCV。升级捕获库后需重新验证
`tests/core/test_build_capture.py`，确认其导入及保存入口仍被正确处理（需安装 `build` 依赖）。

每次编译生成 `build/nuitka-report.xml`，记录模块、DLL 和数据文件的收集来源，便于定位体积增长。
报告不进入发行目录或 ZIP，`--clean` 会同时清理报告。比较体积时应分别记录发行目录和 ZIP 大小，
并使用相同版本、功能和构建选项。

## 发行内容

发行包包含主程序、运行库、主题和图标，以及默认语言包、随包插件和关于页媒体。
构建前调用 `scripts/tutorials/build.py`，从 `docs/tutorials/` 重新生成中英文使用教程和插件开发指南；四份独立离线 HTML
放入成品 `docs/`。教程制作工具、章节源、Markdown、本构建指南及其他开发资料均不随包分发。
`--with-updater` 会加入 `Updater/updater.exe`。个人配置、数据库、Mod、缓存、日志及验证环境
不会复制到发行包。

三个示例插件的发布文件由 `scripts/release/build.py` 的 `SHIPPED_PLUGIN_FILES` 按插件分别列出。
多文件插件必须把包内模块加入该清单；清单导出示例还包含 `inventory.py`。
这份应用发行清单与插件作者的 `plugin.json.files` 分别校验，不能通过本地安装目录自动扩大应用发行内容。

构建脚本生成 `files.manifest`，供更新器识别受管理的发行文件。
语言包和用户数据的保留规则见[更新器说明](../updater/README.md)。

目录模式和单文件模式都会在生成清单和 ZIP 前复制项目许可证及第三方声明，并将当前环境中实际运行依赖
及其传递依赖的许可原文、Python 运行时许可和所需的 Qt、UnRAR 上游补充材料放入 `licenses/`。
依赖按安装元数据的环境标记和请求的 extras 选择，开发、构建专用依赖不会加入。
`licenses/index.json` 记录组件版本、文件路径和补充材料来源；缺少安装元数据或许可文件会中止发行准备。
更新构建环境后应重新安装项目的 `build` 依赖，确保已安装的项目元数据与源码一致。

发行前应在独立目录验证启动、游戏配置、导入和启用、语言切换、插件加载以及更新流程。
同时保留项目许可证、署名和随包依赖的许可材料，参见[第三方声明](../THIRD_PARTY_NOTICES.md)。
